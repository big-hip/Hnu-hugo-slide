# Kubernetes · Volcano · Slurm 调度体系调研汇报

> 调研日期：2026-09-07
> 调研范围：当前基础设施现状梳理、Kubernetes/Volcano/Slurm 三类调度体系原理对比、Slinky(slurm-operator)机制拆解、可选替代方案（Kueue + JobSet）、分布式训练框架现状、选型结论与落地建议。
> 用途：内部技术调研工作汇报。

---

## 一、调研背景与目标

当前 AI 基础设施同时维护两套调度体系：

1. **Kubernetes 集群**：承载模型推理（vLLM / SGLang 等 Serving 服务）；
2. **Slurm（经由 Slinky/slurm-operator 部署在 Kubernetes 内）**：承载 HPC 批处理与深度学习训练作业。

存在的问题：

- 两套体系各记各的账，训练与推理 GPU 池**静态分离**，无法弹性互借；
- 常驻 worker Pod 运维成本与资源冗余高；
- 需要评估是否能用 Kubernetes + Volcano（或其他调度器）统一训练与推理资源池。

调研目标：
- 弄清三类调度体系的能力边界与适用场景；
- 明确 Volcano 能否承接现有 Slurm 训练作业、如何承接；
- 对比 Volcano 与当前更主流的 Kueue + JobSet 方案，给出选型结论。

### 2.2 Slurm（Slinky 方式，部署于 Kubernetes 内）

Slinky 即 **SlinkyProject/slurm-operator**：通过自定义资源（CRD）在 Kubernetes 中部署一套容器化的 Slurm 集群。

![Slinky slurm-operator 架构](k8s_volcano_slurm_assets/slinky-operator-architecture.svg)

*图 1：Slinky slurm-operator 在 Kubernetes 中的组件关系。来源：[SlinkyProject/slurm-operator](https://github.com/SlinkyProject/slurm-operator/blob/f8f955760285153d1498ad843ace848abc9b9022/docs/_static/images/architecture-operator.svg)。*

命名空间 `slurm` 下的核心 Pod：

| Pod | 角色 |
|---|---|
| `slurm-controller-0` | 集群管理中心（slurmctld），作业调度与资源分配 |
| `slurm-login-slinky-*` | 用户登录节点（sbatch / squeue / 写作业脚本） |
| `slurm-restapi-*` | RESTful 接口，K8s 与 Slurm 数据交互桥 |
| `slurm-worker-slinky-0/1` | 实际计算节点（slurmd），GPU 以 GRES 暴露 |

关键事实：
- GPU 以 **`GRES gpu:A100:4 (S:0-1)`** 形式暴露给 Slurm，即每个 worker 提供 4 块 A100 供调度；
- 作业通过 `sbatch` 提交到 `all` 分区，`--gres=gpu:A100:N` 申请显卡；
- worker 与宿主机共享 NFS（`/data/share`），作业镜像以 **apptainer `--nv`** 方式加载运行以透传 GPU；
- 训练作业通常以 `torchrun`（PyTorch 分布式）编排，配合 Megatron 系做张量/流水并行。

## 三、三类调度体系原理对比

### 3.1 Kubernetes 默认调度器（kube-scheduler）

![Kubernetes 组件与控制面架构](k8s_volcano_slurm_assets/kubernetes-components.svg)

*图 3：Kubernetes 控制面与节点组件。来源：[Kubernetes 官方文档](https://kubernetes.io/docs/concepts/overview/components/)。*

- 定位：容器编排平台 + **单 Pod 级**调度；
- 调度单元：单个 Pod，逐个资源匹配（request/limit）；
- AI/批处理短板：
  - 不支持 **gang scheduling**（多 worker 分布式训练容易出现"部分调度、部分等待"的死锁）；
  - 无队列/公平调度语义，仅靠 Namespace + ResourceQuota（能力弱）；
  - 优先级/抢占能力弱；
  - GPU 感知仅停留在"数量"，无算力/显存/拓扑级感知。

### 3.2 Slurm（HPC 作业调度器）

- 定位：**裸机/集群级 HPC 作业调度**，面向科学计算、MPI、深度学习训练；
- 调度单元：**作业（Job）**，整节点或按 slot / GRES 占用；
- 能力：partition（分区）、Queue/QOS（队列/服务质量）、优先级与 fairshare、backfill 回填、作业依赖、超时回收；
- 边界：
  - 与容器生态基本无关（需 apptainer/singularity 等附加一层）；
  - 天然不感知 k8s 的 Service/Deployment、弹性伸缩等；
- 在 K8s 上运行时（Slinky）需要常驻 worker Pod + REST 桥接，仍与 k8s 调度器"两套账"。

![Slurm 架构](k8s_volcano_slurm_assets/slurm-architecture.svg)

*图 4：Slurm 控制器、登录节点与计算节点关系。来源：[SlinkyProject/slurm-operator](https://github.com/SlinkyProject/slurm-operator/blob/f8f955760285153d1498ad843ace848abc9b9022/docs/_static/images/architecture-slurm.svg)。*

### 3.3 Volcano（CNCF 项目，Kubernetes 批量调度器）

- 定位：**Kubernetes 之上的 AI/HPC 批处理调度器**，给 k8s 补齐 Slurm 式能力；
- 部署形态：以 `volcano-scheduler` 作为调度器（或 secondary scheduler）+ `volcano-controller` + admission，提供 CRD：`PodGroup`、`Queue`、`Job`(vcjob)、`ResourceQuota` 等；
- 核心能力：
  - **Gang Scheduling**（集合调度）：`minAvailable` 全部满足才整体调度，杜绝死锁；
  - **Queue + 弹性配额**：多租户队列、weight 公平调度、跨队列 borrow；
  - **优先级 + 抢占**：高优先级作业抢占低优先级空闲资源；
  - **DAG / 任务依赖**：vcjob 内建 job 依赖与策略重试；
- **调度深度**：binpack 装箱、NUMA、GPU 算力/拓扑感知插件；
- 与 k8s 生态原生集成：任务本身就是 Pod/Deployment/Job，无需二次容器化。

![Volcano 架构](k8s_volcano_slurm_assets/volcano-architecture.png)

*图 5：Volcano 控制面、批作业与调度流程。来源：[Volcano 官方文档](https://volcano.sh/docs/home/architecture/)。*

### 3.4 一句话概括三者的本质区别

> - **Slurm**：跑在裸机上的 HPC 作业调度器（作业申请并占用节点资源）；
> - **Kubernetes**：容器编排平台（调度单个 Pod，天然承载容器化服务）；
> - **Volcano**：给 Kubernetes 补齐"Slurm 式批作业能力"的调度器——训练/批作业也直接以 Pod 跑在 k8s 上。

![三类调度体系定位对比](k8s_volcano_slurm_assets/scheduler-comparison.svg)

*图 6：kube-scheduler、Slurm 与 Volcano 的调度单元、优势和适用边界（本报告自绘）。*

### 3.5 重要澄清：Volcano 不等于"完美涵盖 Slurm + k8s"

> 说明：Volcano 的真实价值是"**把 AI 训练与推理统一到 k8s 一套资源池**"，而非完全替代 Slurm 的一切能力。业务若存在传统 HPC/MPI/审计类需求，仍应保留 Slurm。以下为能力边界。

**Volcano 能很好覆盖的部分（面向 AI/ML 训练）**
- Gang 调度、Queue 队列/配额、优先级与抢占、任务 DAG、GPU 计数调度、binpack 放置；
- 与 k8s 生态原生集成（任务即 Pod/Job），推理可直接用标准 Deployment/Service。

**相对 Slurm 缺失或较弱的能力**

| Slurm 能力 | Volcano/k8s 现状 | 潜在影响 |
|---|---|---|
| 作业记账/统计（sacct） | k8s 无原生记账，需外接监控 | 资源使用审计、成本核算不便 |
| 作业 Wall-time 上限（`--time`、超时回收） | 无原生，仅靠 Job `activeDeadlineSeconds` | 长跑作业需自行管控 |
| Reservation（按时段预约资源） | 无 | 无法未来时段预留 |
| Job Array / Job Step / 交互式作业（salloc/srun） | 无一等公民支持 | HPC 脚本迁移成本高 |
| 第一类 MPI 绑定（srun 直包 mpirun） | 需额外 MPI Operator / MPIJob | 传统 MPI 迁移非零成本 |
| Backfill 回填调度 | 有插件但成熟度一般 | 集群利用率提升有限 |
| 任意 GRES 资源（license/自定义/MIG 细粒度） | MIG 支持部分、其他弱 | 异构资源调度受限 |
| QOS / fairshare 全局公平 | 简化版（Queue weight） | 多租户公平性较粗 |
| NUMA/拓扑深度感知 | 有插件，弱于 Slurm 深耕 | 大规模稠密并行受影响 |

**相对 k8s 需要注意的部分**
- Volcano 本身不新增 Service / HPA / Ingress / 存储等云原生能力，这些仍靠标准 k8s 对象（推理任务应保持标准 Deployment，不宜硬套 vcjob）；
- 混用两种调度器管理同一批 GPU 存在**双调度器重复记账/占卡冲突**风险：实践中应整体交给 Volcano 管理，或靠 device plugin + Queue 划清边界。

**对当前环境的分工结论**
- 传统 HPC / MPI / 需要 sacct 记账与时段预约 → **继续保留 Slurm（Slinky）**；
- AI 训练（torchrun / Megatron / DeepSpeed）→ **Volcano** 收益明显（gang、队列、抢占、与 serving 共享资源池）；
- 推荐形态：**k8s + Volcano 管 AI 训练与推理，Slurm 保留给传统 HPC**，按工作负载类型分工，而非互相取代。

## 四、Slinky（当前 Slurm 落地方式）与 Volcano 的对应关系

| 维度 | 现状：Slurm + Slinky | Volcano（纯 Kubernetes） |
|---|---|---|
| 提交流程 | login Pod 里写脚本，`sbatch` | `kubectl apply -f job.yaml` / `vcctl job create` |
| 申请资源 | `#SBATCH --gres=gpu:A100:4` | `resources.limits.nvidia.com/gpu: 4` |
| 占卡方式 | 常驻 worker Pod 提前占卡，作业进入其中 | 无常驻层，作业自己的 Pod 直接占卡 |
| 镜像加载 | apptainer `--nv`（.sif） | Pod spec 直接写容器镜像 |
| 状态查询 | `squeue` | `vcctl job list` / `kubectl get podgroup` |
| 分区/分池 | Partition（静态） | Queue + Namespace（逻辑，可弹性） |
| 图形界面 | 无 | 可对接 KubeRay / Volcano 生态工具 |

关键认知：

> 当前方案是"**先养着常驻 worker Pod 这片卡，再接作业**"；Volcano 是"**来一个作业 → 建一组 Pod → 占这几张卡**"，没有中间常驻层、没有第二套账。

![Slinky 与 Volcano 作业链路对比](k8s_volcano_slurm_assets/slinky-vs-volcano-flow.svg)

## 五、Volcano 落地方式与任务启动

### 5.1 部署（二选一）

```bash
# 方式 A：Helm Charts
helm repo add volcano-sh https://volcano-sh.github.io/helm-charts
helm update
helm install volcano volcano-sh/volcano --namespace volcano-system --create-namespace
```

```bash
# 方式 B：官方 release YAML（需与 k8s 1.35 兼容的 release 分支）
kubectl apply -f https://raw.githubusercontent.com/volcano-sh/volcano/release-1.12/installer/volcano-development.yaml
```

验证：`volcano-scheduler` / `volcano-controller` / `volcano-admission` 在 `volcano-system` 下 Running；存在 `podgroups` / `queues` / `jobs.volcano.sh` CRD。

> 注意：Volcano 默认**不劫持**整个集群，仅接管 `schedulerName: volcano` 的 Pod。普通推理服务可继续走默认 kube-scheduler。

### 5.2 启动 HPC / 大规模训练任务（VolcanoJob，原生支持 gang/队列/抢占/DAG）

```yaml
apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata: { name: dist-train }
spec:
  schedulerName: volcano
  queue: ai-training
  minAvailable: 4            # 4 个 worker 到齐才整体调度（gang）
  policies:
    - event: PodEvicted
      action: RestartJob
  tasks:
    - name: worker
      replicas: 4
      template:
        spec:
          containers:
            - name: train
              image: your-train-image
              resources: { limits: { "nvidia.com/gpu": "1" } }
              command: ["torchrun", "--nnodes=4", "--nproc_per_node=1", "train.py"]
          restartPolicy: OnFailure
```

### 5.3 使用标准 Job + PodGroup（训练/通用批作业，不强求 vcjob）

```yaml
apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata: { name: ai-training }
spec: { weight: 1, capability: { "nvidia.com/gpu": "8" } }
---
apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata: { name: train-group }
spec: { minMember: 4, queue: ai-training }
---
apiVersion: batch/v1
kind: Job
metadata:
  name: train-job
  annotations: { "scheduling.k8s.io/group-name": "train-group" }
spec:
  parallelism: 4
  completions: 4
  template:
    metadata: { annotations: { "scheduling.k8s.io/group-name": "train-group" } }
    spec:
      schedulerName: volcano
      containers:
        - name: train
          image: your-train-image
          resources: { limits: { "nvidia.com/gpu": "1" } }
          command: [torchrun, --nnodes=4, --nproc_per_node=1, train.py]
      restartPolicy: OnFailure
```

### 5.4 推理服务（基本不动，可选择性挂载）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: qwen-vllm }
spec:
  replicas: 2
  template:
    metadata: { labels: { app: qwen-vllm } }
    spec:
      schedulerName: volcano          # 可选：利用 binpack 优化 GPU 放置
      containers:
        - name: vllm
          image: vllm/vllm-openai:latest
          args: ["--model", "Qwen3.8-27B-FP8", "--tensor-parallel-size", "2"]
          resources: { limits: { "nvidia.com/gpu": "2" } }
---
apiVersion: v1
kind: Service
metadata: { name: qwen-vllm }
spec: { selector: { app: qwen-vllm }, ports: [{ port: 8000 }] }
```

## 六、资源不足时的行为（排队 or 失败）

| 场景 | 行为 |
|---|---|
| 训练任务（带 gang，如 `minAvailable=4`） | 缺卡 → 整个 Job **Inqueue（排队等待）**，不会部分启动（避免死锁），卡够自动运行 |
| 推理任务（Deployment，无 PodGroup） | 缺卡 → 该副本 Pod **Pending**，已有副本继续服务，不失败，卡够自动补副本 |
| 队列配额不足 | 作业进入队列等待或跨队列 borrow，默认**不拒绝** |
| 配置优先级 + 抢占 | 高优先级作业可抢占低优先级空闲 GPU |
| 希望超时失败 | 需在 Job `policies` 显式配置（如 `PodUnschedulable → AbortJob`），默认不会主动失败 |

查看方式：

```bash
vcctl job list               # Pending / Inqueue / Running / Completed / Aborted
kubectl get podgroup
kubectl describe podgroup <name>
```

小结：**默认是"排队等待"而非"直接失败"**；训练整组等、推理单副本等。可通过优先级/抢占/Queue 配额/失败策略四类配置精细化控制。

## 七、进阶方案对比：Kueue + JobSet vs Volcano

![Kueue 架构](k8s_volcano_slurm_assets/kueue-architecture.svg)

*图 9：Kueue 的工作负载准入、LocalQueue 与 ClusterQueue 关系。来源：[Kueue 官方项目](https://kueue.sigs.k8s.io/)。*

![JobSet 编排关系](k8s_volcano_slurm_assets/jobset-diagram.png)

*图 10：JobSet 对多个关联 Kubernetes Job 的编排。来源：[JobSet 官方项目](https://jobset.sigs.k8s.io/)。*

| 维度 | Kueue + JobSet | Volcano |
|---|---|---|
| 定位 | 排队/配额/准入控制，任务仍是标准 Job/JobSet，不替换调度器 | 完整调度器 + 自有 CRD（PodGroup/Queue/vcjob），深度接管调度 |
| 学习/锁定成本 | 低，无私有任务 API | 较高，概念多，且调度器接入方式需谨慎（替换或 secondary） |
| Gang 调度 | JobSet `jobStartPolicy` 实现，语义简单 | 原生内建、可调性强 |
| 调度深度（NUMA/拓扑/GPU算力/MIG/预留/DAG） | 不强（高速调度交给别的调度器如 NVIDIA KAI） | 强，插件齐全 |
| 生态 | CNCF；EKS/GKE 官方推荐，GitOps/算子兼容好 | CNCF，AI/ML 批调度史长（华为云等亦有支持） |
| 典型组合 | Kueue + JobSet +（可选）NVIDIA KAI | Volcano 独立即可 |

选型结论（针对当前 3 节点规模）：

- **默认推荐 Kueue + JobSet**：负担小、不锁定、可随时退回标准用法；TP2/DP 这类浅调度语义，JobSet 的 gang 已足够。
- **仅当需要** GPU 拓扑绑定、NUMA、MIG/MPS、显存/算力感知等高阶调度时才考虑 Volcano 或 NVIDIA KAI。
- 两者可叠加使用（Kueue 管队列，Volcano/KAI 管实际放置），但对当前规模属于自找复杂度。

> 补充：NVIDIA 官方当前路线为 **NVIDIA KAI Scheduler**（GPU 感知调度：binpack、gang、MIG、拓扑感知），常与 Kueue 组合；YuniKorn（Apache）偏大数据多租户队列，适合已有 Hadoop 体系的情形。

## 八、分布式训练框架现状（与调度器的关系）

调度器只负责"资源何时/何地给"，实际并行训练由以下框架完成：

| 层 | 技术 | 说明 |
|---|---|---|
| 基础并行 | **PyTorch 分布式（NCCL）** | `torchrun` / `torch.distributed`，DDP 数据并行；FSDP 参数分片（ZeRO-3 式） |
| 显存优化 | **DeepSpeed** | ZeRO 0/1/2/3、Offload、Ulysses 序列并行、MoE 支持 |
| 大模型并行 | **Megatron-LM / Megatron-Core** | 张量并行 + 流水并行 + 序列并行（3D 并行），预训练主流 |
| 组合方案 | **Megatron-DeepSpeed** | 超大模型标准组合 |
| 编排 | **Ray / Ray Train / KubeRay** | 纯 Python 分布式编排，vLLM 的分布式引擎即 Ray；在线 RL（RLHF/GRPO）几乎必用；可跑在 k8s 上 |
| 推理配套 | **vLLM / SGLang** | Serving 与 RL rollout 环境 |
| 后训练 | OpenRLHF / TRL / NeMo-Aligner | RL/对齐 |

当前环境采用：**Slurm + torchrun + Megatron（训练）** + **vLLM/SGLang（推理）**，与行业主流一致。

---

## 九、调研总结与建议

1. **当前两套体系（k8s 推理 + slurm 训练）本身可运转**，瓶颈在运维冗余与 GPU 池无法弹性互借；
2. **统一方案首选 Kubernetes 生态**：训练/推理共享 GPU 池，用 Namespace + Queue 逻辑隔离，可借调/抢占；但需明确 Volcano 是"AI 训练统一"，**不追求替代 Slurm 的全部能力**（详见 3.5 能力边界），传统 HPC 仍保留 Slurm；
3. **调度器选型**：小规模（≤10 节点）下 **Kueue + JobSet** 性价比最高；需要深度 GPU/拓扑控制时选用 **Volcano** 或 **NVIDIA KAI**；
4. **若上 Volcano**：可按第五节直接部署与启动任务，服务层（vLLM）无需改动，训练从 `sbatch` 迁移到 `kubectl/ vcctl` 即可，且获得 gang/队列/抢占能力；注意双调度器混用的资源记账风险，需划清 Queue 边界；
5. **原有 Slurm/Slinky 无需立即废弃**：保留承担传统 HPC/MPI/需记账类作业，作为过渡期通道与 Volcano 并行，验证稳定后再按负载类型收敛；
6. **落地序**：① 最小化部署 Volcano 或 Kueue+JobSet → ② 建立 Queue 与优先级模型 → ③ 迁移 1~2 个代表性训练/推理任务（如 Qwen 评测作业、vLLM Serving）做冒烟验证 → ④ 对比资源利用率与运维成本 → ⑤ 决定是否全面切换。
